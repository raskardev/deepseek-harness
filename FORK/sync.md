# Syncing with upstream

## Remotes

`origin` is the fork. Add upstream once:

```sh
git remote add upstream https://github.com/deepseek-ai/deepseek-harness.git
git remote set-url --push upstream DISABLED   # the fork never pushes upstream
git fetch upstream
```

## Branch model

- `master` on the fork tracks `upstream/master` plus fork commits. Fork work happens on `<type>/<slug>` branches merged into `master`.
- Sync by **merging** `upstream/master` into `master`: `git fetch upstream && git switch master && git merge upstream/master`. Do not rebase `master` or any pushed branch onto upstream; the fork history is shared with its own PRs.
- Keep fork-only changes in separate commits that touch as few upstream files as possible, so `git log upstream/master..master` reads as the fork's patch set.
- Sync before starting a branch and before opening a PR, not in the middle of one. After a sync, merge `master` into open branches instead of rebasing them.
- Upstream stacking tooling (`gh stack`, the `dsh-merging-stacked-prs` skill) assumes every branch lives in the upstream repository. In the fork, open PRs against `raskardev/deepseek-harness` `master` only, one branch per PR.

## Conflict hot spots

Upstream merges tens of PRs a day; these paths conflict on almost every sync when the fork touches them:

| Path | Why | Resolution |
| --- | --- | --- |
| `pnpm-lock.yaml` | regenerated by every dependency change | take upstream, then `pnpm install` and commit the result |
| `scripts/*.manifest.json` (`doc-budgets`, `translation-pairing`, `type-equiv`) | gate state | take upstream, re-apply fork entries, rerun the owning gate |
| `docs/config-catalog.md`, other generated catalogs | generator output | take upstream, rerun the generator (below) |
| `*.i18n.yaml` sidecars | section hashes of a `.md` / `.zh.md` pair | take upstream, then `pnpm exec tsx scripts/verify-translation-pairing.ts --write <pair>` for each pair the fork edited |
| `website/docs.ts` | website page manifest | take upstream, re-add fork entries |
| `AGENTS.md`, `docs/architecture.md` | edited by most architectural PRs | avoid fork edits; put fork rules in `FORK.md` |
| `.github/workflows/*` | upstream CI tuning | see [ci.md](ci.md); keep fork patches minimal |

## Generated artifacts checklist

After resolving a conflict in a generated file, never hand-merge it: take the upstream side, then regenerate.

1. `pnpm install` if `package.json` or `pnpm-lock.yaml` changed.
2. Run the generator that owns the file. Generators are the `gen-*` scripts in the root `package.json` (`gen-config-catalog`, `gen-tool-catalog`, `gen-cordis-catalog`, `gen-persistence-catalog`, `gen-session-format-catalog`, `gen-cli-help`, `gen-tsconfig-paths`, and others); the file header or the failing gate names its generator.
3. `pnpm run test:docs` for the quick documentation checks, then `pnpm run doc-sync` when docs or generated catalogs changed. A stale artifact fails here with the command that refreshes it.
4. `pnpm run typecheck` and the focused tests for any package the fork changed.
5. Commit the merge with the regenerated files in the same commit.

## Upgrade guides

Upstream records breaking changes in `docs/upgrade-guide/v<version>/`. Read the guides for every version crossed by a sync before merging; they list renamed config keys, profile changes, and persisted-data migrations that fork patches and local profiles in `%USERPROFILE%\.dsh` may need to follow.
